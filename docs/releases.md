# Releases

**Status: accepted.**

What this repository releases, how each is versioned, and what a release does. The steps, with what publishing 0.1.0 taught, are in [RELEASING.md](../RELEASING.md). Two things are released, apart: **the spec**, and **the implementation** (the npm packages and the crate). Drafts follow `main`; releases are frozen.

## Decisions

1. **The spec's releases are tags `spec-v<major>.<minor>`**, such as `spec-v1.0`. A tag freezes the spec as it is at that commit: the website gives it an address of its own, `/spec/1.0/`, which never changes. Until version 1 is released, the spec is a draft, published from `main` with a "Draft" banner, and `/spec/` is the draft; after it, `/spec/` is the latest release and `/spec/draft/` the draft ([the website's design](../website/docs/design.md), decision 11). **Each revision of a draft is numbered and tagged** (decided 2026-11-17, spec §1): `1.0-draft.N`, N going up by one with each revision, written in the spec's header, its companion's and the changelog entry's heading, and tagged `spec-v1.0-draft.N`. A change to the spec or its companion goes under `### Unreleased` in the changelog, which makes the spec *dirty*; so does any change to their files since the tag of the revision the header names, written there or not. Before a push of spec changes, `cargo make spec-revision` cuts the next revision (the heading and both headers, today's date, a commit and its tag), and `git push --follow-tags` pushes the tag with it. A release's revision is cut the same way, `cargo make spec-revision --release`: `1.0` from `1.0-draft.N`, tagged `spec-v1.0`. A cut is whole or not at all (added 2026-11-24, audit B26): an existing tag, or a current revision without its tag, stops it before anything is written, and a commit that fails puts the three files back. The spec may be dirty locally, and `cargo make ci` passes; a push to `main` (CI's `spec-revision` job) and a release (the release workflow) fail while it is (`cargo make spec-check`). No tag starts the Pages workflow: a draft's tag makes no page of its own (the site's pages follow `main`), and a release's page comes with the push of its commit to `main` (decision 7).
2. **The implementation's releases are tags `v<major>.<minor>.<patch>`**, such as `v0.2.0`, and its version is [semantic](https://semver.org). It is one version for every package: `@compmd/processor` and `@compmd/render` are released together, always with the same number, since the processor depends on the renderer's types; the crate `compmd` takes the same number once it is published.
3. **`0.x` until the spec's version 1 is released.** While the spec is a draft, the implementation is `0.x`, and any minor release may break, as semantic versioning allows below `1.0.0`. With the spec's version 1, the implementation becomes `1.0.0`, and a breaking change needs a new major version from then on. The spec never names an implementation's version; each implementation names the spec's it implements: `compmd::SPEC_VERSION` in the crate, `SPEC_VERSION` in `@compmd/processor`, and each implementing package's README, which tests keep the same. Between releases the spec may move ahead of the code, so a spec change can be written and checked locally before the code follows; **a release must implement the spec's revision at its commit** (decided 2026-11-17): the release workflow fails when `SPEC_VERSION` isn't the spec header's revision.
4. **npm gets releases only.** A published version can never be changed, and applications pin to it, so nothing is published from `main`: no `next` versions, since the playground already shows the latest `main`.
5. **A release tag publishes from CI**, by a workflow of its own (`.github/workflows/release.yml`): it builds, runs `cargo make ci`, and stages every package with npm's trusted publishing. GitHub proves to npm which repository and workflow publishes, so no npm token is stored anywhere, and each version carries its provenance: where and from what it was built. **A staged version is installable once the author approves it**, with two-factor authentication: the trusted publishers allow staging alone, so CI builds and checks, and the author releases (decided 2026-11-02). **The crates are published by the same workflow** (decided 2026-11-03), once the npm packages are staged, with crates.io's trusted publishing: crates.io has no staging, so their job waits in a GitHub environment, `crates-io`, for the author's approval, and the crates' trusted publishers name that environment. `compmd` and `tauri-plugin-compmd` (from 0.6.0) take the release's version; `compmd-markdown`, the fork, its own, published only when it changed.
6. **The first version, `0.1.0`, is published by hand**, by the author: trusted publishing is set up on packages that already exist on npm.
7. **The website follows `main`** (decided 2026-11-25, audit I8 and B23, replacing "the website shows the latest release"): it deploys on a push to `main`, never from a tag. Its snippets are `main`'s and run as tests against `main`'s code, so a change can't leave them broken; between releases they can be ahead of the version on npm. Its install line names no version, so it always installs the latest release. A released spec's page comes with the push of its commit to `main`, whose run fetches every tag.
8. **Packs this repository publishes are released on their own**: each has a version of its own and a tag `<pack>-v<version>`, published by trusted publishing. The first was the Mermaid pack, `@comp-markdown/mermaid` ([its design](mermaid-pack.md), decision 9); the second, the wireframe pack, `@comp-markdown/wireframe` (2026-11-19). **With about 25 packs, three commands and one workflow do it for all of them** (decided 2026-11-20, CR-28), each command with `--dry-run`, which says what it would do and does nothing:
   - **`cargo make pack-placeholders <pack>...`** creates new packs on npm: for each one npm doesn't have, it publishes the `0.0.0` placeholder of *A placeholder first* (RELEASING.md), written outside the repository, then sets its trusted publisher with `npm trust github` (the repository, `release-packs.yml`, staging only, `--allow-stage-publish`). One one-time code covers the run while it is valid; npm allows about 80 packages in its 5-minute window.
   - **`compmd-packs/versions.json` is the one place a pack's version is written** (`{ "card": "0.1.0", … }`); each pack's `package.json` and its document's `export.version` follow it, and `cargo make ci` fails when one doesn't (`cargo make pack-versions`). **`cargo make release-packs`** writes the versions into the packs' files when they differ (then stops, for a commit), asks npm which of those versions it doesn't have, shows them, and on the author's yes tags each `<pack>-v<version>` at `main`'s pushed commit, pushes the tags and starts one run of **`release-packs.yml`** (`gh workflow run`), which runs `cargo make ci` once and stages every pack tagged at its commit whose version npm doesn't have: one run for a batch, not one per tag. It is started by hand, not by the tags: GitHub starts nothing for a push of more than three tags at once.
   - **`cargo make approve-packs`** lists what is staged for every pack as checkboxes (`@inquirer/checkbox`), all chosen; Enter approves the chosen ones (`npm stage approve`) in the order they were staged.

   The Mermaid and wireframe packs are released the same way: `release-mermaid.yml` and `release-wireframe.yml` go, and their trusted publishers are revoked (`npm trust revoke`) and set again for `release-packs.yml`, since a package has one and its workflow can't be changed. The commands run a pinned npm with staging and `npm trust` (11.15 or newer), as the release workflow does.

9. **The language server, `compmd-lsp`, is released with the implementation, as binaries an editor installs** (decided 2026-11-25, CR-150; built in CMD-32; [editor support](editor-support.md), decision 9). The same tag `v<version>`, the same version.
   - **Six binaries**, one per platform, each built on a runner of its own: `aarch64-apple-darwin` and `x86_64-apple-darwin` (macOS, both on `macos-15`, which cross-compiles to Intel), `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` (Linux, on `ubuntu-24.04` and `ubuntu-24.04-arm`; musl, so one binary runs on every distribution, whatever its glibc), `x86_64-pc-windows-msvc` and `aarch64-pc-windows-msvc` (on `windows-2025` and `windows-11-arm`). A job `lsp`, a matrix of the six, runs `cargo build --release --locked -p compmd-lsp` and checks the binary answers `--version` with the release's version; like `build`, it has no `id-token` and no write permission, and uploads the binaries as an artifact.
   - **On the GitHub release**, a job `github-release`, once `stage` and `crates` have run: the release `v<version>` with each binary as `compmd-lsp-<version>-<target>` (`.exe` on Windows, each a bare binary, not an archive) and `SHA256SUMS`, the sums of all six. It has `contents: write` and nothing else, checks nothing out and runs nothing of the repository's, as `stage` does: it downloads the artifact, writes the sums with `sha256sum` and runs `gh release create`. A dry run builds the binaries and creates no release.
   - **On npm, `@compmd/lsp`** with a package per platform as optional dependencies, as esbuild and Biome ship theirs: `@compmd/lsp-darwin-arm64`, `@compmd/lsp-darwin-x64`, `@compmd/lsp-linux-arm64`, `@compmd/lsp-linux-x64`, `@compmd/lsp-win32-arm64`, `@compmd/lsp-win32-x64`, each with its `os` and `cpu` and the binary, so npm installs only the one that runs. `@compmd/lsp` holds a `bin` script, `compmd-lsp`, which finds the platform's package and runs its binary with the same arguments and stdio. The platform packages are written by the `build` job from one template in `npm-packages/lsp/` and the `lsp` job's binaries, and staged with the others, before `@compmd/lsp` (`PACKAGES` lists `lsp`; the platform packages go before it). Each is created on npm by a placeholder `0.0.0`, with its trusted publisher (staging only), before the first release: the author's step, as `@compmd/devtools`' was.
   - **On crates.io, `compmd-lsp`** (`cargo install compmd-lsp`), with the crates it depends on: `compmd-project` and `compmd-components`, published from the same release in the `crates` job, after `compmd` and `compmd-host` and before `compmd-lsp`. Each is created by a placeholder `0.0.0`, as `tauri-plugin-compmd` was, with its trusted publisher.
   - The build's version check covers the new crates and packages too, and RELEASING.md lists them in its table, its version list, its order and its checks.

## A release, step by step

1. The changelog's entries for the release are written, and `cargo make ci` is green on `main`, and so is the Tauri check (`tauri.yml`); `cargo make tauri-check` on a Mac checks it in WKWebView, which CI doesn't run ([CI](ci.md), decision 13).
2. The version is set in every package's `package.json`, in `crates/processor/Cargo.toml` and in `crates/tauri/Cargo.toml`, in one commit.
3. The tag `v<version>` is pushed; the release workflow publishes. The website isn't deployed by the tag: it already shows `main` (decision 7).

A release of the spec is a tag `spec-v<version>` on a commit whose changelog says what the version holds; the website deploys with its new address.

## The release workflow

`.github/workflows/release.yml` runs on a tag `v*`. It runs the Tauri check first (`tauri.yml`, called as a job), and publishes nothing unless it passes. It checks the tag is the version in both `package.json` files and that `compmd::SPEC_VERSION` is the spec's revision at the commit, runs `cargo make ci`, packs both packages with pnpm (which writes the renderer's version into the processor's dependency), and publishes them with npm 11.6.2 by trusted publishing, the renderer first. (Changed 2026-11-25, audit S25: a `build` job without `id-token` checks and packs every package `PACKAGES` lists, and a `stage` job with it only downloads the tarballs and stages them; `workflow_dispatch` runs it as a dry run. RELEASING.md has the details.)

It needs both packages to exist on npm, and each set up once on npmjs.com (the package's settings, **Trusted publisher**, GitHub Actions): the organization `comp-markdown`, the repository `compmd`, the workflow `release.yml`, no environment.

Its second job, `crates`, runs in the environment `crates-io`, once the author approves it: `compmd-markdown` from the fork when crates.io doesn't have its version, then `compmd` and `tauri-plugin-compmd` with the release's number (the plugin with the frames the release job built), each with a token `rust-lang/crates-io-auth-action` gets by trusted publishing. Each crate's trusted publisher on crates.io names the organization `comp-markdown`, the repository `compmd`, the workflow `release.yml` and the environment `crates-io`.
