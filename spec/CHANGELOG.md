# CompMD spec changelog

Changes to the [CompMD specification](compmd-spec-v1.md) and its companion, [*CompMD packs on a registry*](compmd-registry-v1.md), newest first. Every change to either adds an entry here, naming the sections it touches. Version 1 is a draft until it is published; until then, a change can break documents written against an earlier draft, and its entry says so. Each entry is a revision of both, `1.0-draft.N` with its date (spec §1), tagged `spec-v1.0-draft.N`. A change goes under `### Unreleased`, at the top, until the next revision is cut (`cargo make spec-revision`, [releases](../docs/releases.md), decision 1).

## Version 1 (draft)

### Unreleased

- **Inline styles apply in a component's box (§7.4, §15).** In the document a component's `target` is in, a `style` attribute and a `<style>` element it writes, or a library it uses writes, apply, and a processor MUST provide that wherever it mounts a component; a sandbox's frame does by its policy, which the informative note on browsers now says allows inline styles, safely, since CSS reaches out only by requests. A host whose page refuses inline styles keeps such components in frames, or allows inline styles where they run, and SHOULD NOT loosen its page only for them. Trusted code takes no CSS from a param, as it takes no HTML. Not breaking: the frames allowed inline styles already; a trusted component in a page that refused them didn't draw right before either.
- **Rows of one height (§9, §9.4).** `box` and `grid` take `grid-auto-rows` (type `tracks`, with breakpoints), CSS's property: `::: grid {min=14rem grid-auto-rows=1fr}` makes every row of cards as tall as the tallest, which `grid-template-rows` could do only for a known number of rows. Not breaking.
- **Fonts of a document's own (§2.1, §6, §8.6, §9.2, §9.4, §10.2, §12.3).** `md.fonts` declares fonts by name, each with its `files` (relative `.woff2` or `.woff` paths, by `weight` and `style`) and a `fallback` token (`body` by default), from the document's folder or a pack's, never from a URL; `font-family` takes the name besides the tokens. A pack exports and imports fonts as it does components, by `fonts` beside `names`, which takes the same entries; an import or export now needs `names`, `fonts` or both. Font names resolve as component names do, in names of their own, where they are written, an expression's value too. The expanded tree's root lists the fonts its params use, in `fonts`, a `font-family` param naming one by its `family`; a file the host can't serve shows the fallback. New uses of F009, F013, F021, F023 and F026 for them. Not breaking: `font-family` took tokens only, and `md.fonts` was an unknown key (W111).
- **A component's text in its box's type (§7.4, §7.6).** The type params reach a host-language component two ways: what it draws with CSS inherits them, in the page or, from a sandbox, in a frame whose root is given the type its box shows; and the context has `type` (`family`, `size` in pixels, `weight`, `style`, `color`, `lineHeight`, `letterSpacing`), for one that sets its text's type itself, `update` called when it changes. The React and Svelte bindings pass it in the `compmd` prop. Not breaking: a component that ignores both works as before.
- **A document's language and direction reach its page (§2.1, §7.8, §12.3).** The expanded tree's root has `lang` and `dir` when the document writes `md.lang` or `md.dir`, `dir` from the language's script when only `lang` is written; a renderer sets them on the element it renders into, and on an example's box from the example's own root, and a host writing a page of its own sets them on the page. Before, they reached no renderer: an Arabic document showed left to right unless its host set the direction itself, and an Arabic example in an English page always did. The tree schema has both. Not breaking: a document that writes neither keeps where it is shown's.
- **Type in a box (§9.2, §9.4, §10.2).** Ten common params set the type of a box's text, as CSS's properties of those names do, inherited by what it holds: `font-size` (`s`, `m`, `l`, `xl` in `em`, or a length), `font-weight` (`normal`, `bold`), `font-style` (`normal`, `italic`), `font-family` (`body`, `heading`, `mono`, the host's fonts, never a font's name), `color` (`muted`, `accent` or a CSS color), `text-align` (`start`, `center`, `end`), `line-height` (`tight`, `normal`, `loose` or a number), `letter-spacing` (`tight`, `normal`, `wide` or a length), `text-transform` and `text-decoration`, all with breakpoints, on inline boxes too. The tokens are custom properties with defaults (`--compmd-text-*`, `--compmd-font-*`, `--compmd-leading-*`, `--compmd-tracking-*`). W126 (new) is a box whose `color` and `background`, both opaque colors in hex, `rgb()` or `hsl()`, contrast below 4.5:1. Breaking for a signature that declares a param of one of these names (`color`, say), which is now F013, as for the other common params.
- **An image cropped to its box (§9.2, §10.2).** An image box, a `box` whose expanded content is one paragraph holding one image (alone or as a link's only content), fits its image by `object-fit` and `object-position` as a component's box fits its drawing: the image takes the box's inside, so the box's height (`height`, `aspect-ratio`, `fill`, a stretching layout) crops it. A definition makes one around an image it is given. On a box that is neither a host-language component's nor an image box, the two params are W125 (new), at the box. Before, they meant nothing to any box but a component's. Breaking only for a box around one image that had them, which now fits its image; any other such box now warns.
- **A placed block's box, sized by its flow (§9.2, §10.2).** A box that places blocks by position takes its height from the blocks left in its flow, as an article with a note pinned on it does; W119 is now for a box whose blocks are all placed, with no `height`, `aspect-ratio` or `fill`. Before, any box that placed a block needed one of those params. Not breaking: fewer warnings.
- **A component fits its box (§7.4, §7.6, §9.2).** Two common params say how what a host-language component draws sits in its box: `object-fit` (`contain`, the default, `cover`, `fill`) and `object-position` (one or two of `start`, `center`, `end`, block then inline; `center` by default), with CSS's meanings, written without a breakpoint (F008 with one). The component gets them in the host contract as `fit` (`mode`, and `x` and `y` resolved with the box's direction), and the React and Svelte bindings pass it. §7.4 says a component takes its box's inside, its width and its height when the box has one, a drawing with an aspect ratio sitting in it as `fit` says (SHOULD, with no size params of its own); a component's natural size is CSS's (300 pixels wide for a drawing with only a ratio, 300 by 150 with none, a script-sized drawing containing its size); and a processor that runs a component elsewhere than the document that lays it out (a sandbox's frame) MUST lay its use out as if it ran there. Not breaking, but for a component that declares a param named `object-fit` or `object-position` (below).
- **Sizes include padding and border (§9.2).** `width`, `max-width` and `aspect-ratio` measure a block with its padding and its border; the spec said padding only. Not breaking.
- **A signature fence's param list (§7, §10.2, §11, §12.1, §12.3).** A signature fence may end with a param list, taking what a host-language definition fence takes: it gives the box of the component it attaches to its defaults, the caller's params over them, so a built module, which has no definition fence, still sizes its box (`{width=12rem max-width=100%}`). F036 now means a component whose definition fence and signature fence both style its box, reported at resolving, the definition fence's list kept; before, any param list on a signature fence was F036, at parsing, and ignored. The parse tree's `componentSignature` has `params`. Not breaking: only documents that had F036 change.
- **The processor's names (§5.1, §10.2).** A signature that declares a common param, `lang` or `dir` is F013, as one that declares `class` or `id` already was: the processor applies them to the box and never passes them on, so such a param never reached the component. Breaking for a signature that declares one of them, which now has F013, the param dropped.
- **What a definition's body knows of its invocation (§7.2, §8.1).** `md.fallback` is a leaf's or an inline invocation's fallback in its body, rendered in text and its plain text in an image's alt, where interpolation is now allowed too; in a container's body it is F014. `md.slots.<name>` is whether the caller gave that slot, in the definition's expressions. Not breaking: `md.` names were reserved.
- **A destination from the caller resolves against the caller (§8.6).** In a definition's body, a link's or image's destination that starts with an interpolation of a param, a field of one, or an `each` or template slot name over one resolves against the caller's document, as slot content does; one that starts with literal text keeps the definition's file. Not breaking for a destination given as a path from the caller's folder, which was resolved against the pack before.
- **An optional enum (§7.3).** The declarations' example shows one, `level: L | M | H | Q?`, and a rule says the `?` applies to the whole enum, not to its last member: the grammar allowed it already (`?` follows any type, an enum among them). A conformance case checks it. Not a change: nothing new is allowed.
- **A definition's own files reach the output (§8.6, §12.3).** The expanded tree resolves the relative destinations of links and images from a definition's body: one in another file of the root folder is written relative to the processed document, and one in a pack is the file's place (`@acme/kit@1.4.2/icons/star.svg`) with `pack: true`, which a renderer asks its host to map to where it serves the pack's files. Before, they were kept as written, so they led to files next to the processed document that weren't there. Not breaking for documents; a renderer maps `pack` destinations, and a host serves every file of its packs.
- **An inline invocation's box (§7.2, §12.3).** An inline invocation of a `compmd` component is one inline box, styled by its fence's params under the caller's, a `componentInline` named `box` in the expanded tree; before, it had no box and the fence's params didn't apply. Breaking only for an inline definition fenced with params, which now apply.
- **`stretch-link`, `shadow`, `rotate` and `border`'s sides (§9.2, §9.4, §10.2).** `stretch-link`, a flag with no breakpoint, makes a box's first link cover the box (W124 with no link in it). `shadow` takes `none`, `s`, `m` or `l` (`--compmd-shadow-*`), `rotate` an angle from `-15deg` to `15deg` (types `shadow` and `angle`), and `border-inline-start`, `border-inline-end`, `border-block-start` and `border-block-end` `border`'s values, `border` covering them in a fence's cascade. Not breaking, but for a signature that declares a param of one of these names, which is now F013.

### 1.0-draft.17, 2026-11-20

- **Every origin, for a host's own documents (§8.6, §15).** A host MAY allow every origin instead of naming them: then no origin of a document's data or images is disallowed (F028) or asked about. It fits documents the host publishes itself, such as a static site's or a blog's; a host that shows documents others write SHOULD NOT. URL schemes, a data `from`'s literal scheme and host, credentials and sandboxes' network are unchanged. Not breaking.

### 1.0-draft.16, 2026-11-19

- **WebAssembly in a sandbox (§15).** The informative note on browsers says a sandbox's policy may allow compiling WebAssembly (`'wasm-unsafe-eval'`), since WebAssembly reaches only what the frame's scripts reach. No rule changes. Not breaking.

### 1.0-draft.15, 2026-11-18

- **The spec's folder.** The spec, its companion, this changelog and `llms.txt` are in the repository's `spec/` folder, with the complete example in `spec/examples/complete/`; the spec's links to the repository's files follow. The spec itself is unchanged.

### 1.0-draft.14, 2026-11-18

- **Examples (§6.3, §7.8, §8.7, §10.2, §12.3).** A ` ```compmd ` block with `render=output` or `render=both` is an example: its text is processed as a document of its own (its own frontmatter, imports, data, inputs and definitions, resolved from the document's place, with its permissions), and what it renders shows in its place, after the code with `both`. Its param list takes `render`, the common params, `class` and `id` (F008 otherwise); its diagnostics are at their places in the document; a ` ```compmd ` block inside it shows its source (W123, new). The expanded `code` node has `params` and `document`, the example's root, numbered by `example`, and an example's host-language components are listed with its number. `render` on a ` ```compmd ` block is `source` by default, so no document changes. Not breaking.
- **What a rendered block shows (§5.1, §7.7, §10.2, §12.3, §14).** A code block a code renderer renders takes `render`: `output` (what the component draws, the default), `source` (the code block alone, the component not run, no `alt` needed) or `both` (the code, then the drawing, in one box). It is bare only (F009 otherwise), the processor's (the component never gets it), and on the expanded tree's `code` node; plain renderers and plain text show the code, printing what shows. A signature that declares `class` or `id`, or a code renderer's that declares `alt` or `render`, is F013: those names are the processor's. Breaking only for a signature that declares one of them.
- **A container's plain text (§14).** The plain-text paragraph says that a container's fallback is its slots, so the components in them, nested containers among them, give their fallbacks at any depth, and an `if` gives both its branches, as §4.5 has it. Not breaking.

### 1.0-draft.13, 2026-11-17

- **Version numbers (§1).** The spec and its companion are versioned on their own, apart from any implementation's: `MAJOR.MINOR`, with drafts `1.0-draft.N`, one for each revision, the entries here numbered from the first; each revision is tagged `spec-v1.0-draft.N`, changes wait under "Unreleased" until the next one, and an implementation states the version it implements. Before, the spec said only "version 1, draft" and a date. Not breaking.
- **A document's plain text (§14).** An informative paragraph says what a processor gives as a document's text as a reader reads it, for a search index or a preview: one line per block, without syntax markers, URLs, raw HTML, the frontmatter, component lines or definitions, with labels, alt text, code, math and components' fallbacks kept. Not breaking.
- **Printing (§7.3, §10.2, §12.3, §14).** A host-language component's signature may say `print: fallback`: on paper, each use of the component shows its fallback (§4.5), for a component that means nothing there, an interactive map or a video; the default, `drawn`, prints it as drawn. Any other value, or `print` in a `compmd` definition, is W122. The signature in the tree has `print: "fallback"` when it says so. §14 says, informatively, how a processor prints: the document as it renders it, light on paper unless the host says otherwise, after its components have drawn. Not breaking.
- **TOML frontmatter (§2.1, §10.2, §12.2).** Frontmatter may be TOML between `+++` lines as well as YAML between `---` lines, and says the same: dates and times as strings, numbers, booleans, tables as mappings in order, arrays of tables as lists of mappings. Text that isn't TOML, a duplicate key among it, is F033, as is one over the size cap; the tree has it as a `toml` node with `parsed`. Before, `+++` was ordinary text. Breaking only for a document that starts with a `+++` block meant as text, which is now its frontmatter.
- **Remote images are asked about (§8.6, §15).** A document's images with a remote URL, in Markdown or raw HTML, are fetches at view time: a processor that shows them while a reader views the document MUST ask the reader about the image's origin, as about data, with one answer per origin for both, in every way it shows a document. Until the origin is allowed, the image shows its alt text, with a way to allow the origin. Before, the spec named images only as the baseline of what a fetch reveals, so an author could learn who opened a document from its images. Not breaking for documents; a processor that loaded remote images without asking now asks.
- **Text after a short-form default (§7.3, §10.2).** A declaration's short-form default is one param value, so an unquoted one ends at its first white space, and text after it is F011, with a fix that quotes the default. Before, the spec didn't say, and `string = Klara and the Sun` silently gave the default `Klara`. Breaking for such documents only, which now get F011 where they got a cut default.
- **A host's own URL schemes (§15).** A link, a link reference, a wiki link or an image, in Markdown or raw HTML, renders when its URL is relative or uses `https:`, `http:` or `mailto:`, or a scheme the host names as its own (an application's `app:` for its own pages and files); a link with any other renders its text, an image its alt text. The host resolves its own schemes: it handles a click on such a link, and loads such an image, which is never asked about as a remote image is. A host can't name `javascript:`, `vbscript:`, `data:`, `blob:` or `file:`. Before, the spec restricted schemes only in interpolated URLs (§8.1), and a host had no way to link to its own pages, or show its own files, from a document. Not breaking: a host that names none renders links and images as before.

### 1.0-draft.12, 2026-11-12

- **A pack's source compiled ahead (§6.4).** A processor may compile a pack's source component file once, before a document needs it, and load the result by the file's place, as it may a built module: the same code, at the same trust. Before, the spec said nothing of where a source component is compiled. Not breaking.

### 1.0-draft.11, 2026-11-10

- **A registry pack however it was got (§6.4).** A pack a host installed with an application, keeps in its own store of published versions, or fetched while a reader views the document is a registry pack all the same: checked against its integrity, at the trust its configuration gives it and never trusted, and cacheable by its place. Before, the spec said this only of packs fetched from a registry, and a host could read an installed or marketplace pack as its own. Not breaking.

### 1.0-draft.10, 2026-11-03

- **A component still drawing (§7.4, §7.6).** The context gains `busy(work)`, which a component calls with a promise of a drawing it makes after `mount` or `update` returned, and the React and Svelte bindings pass it in the `compmd` prop. A processor that waits for its page to settle (to print, to scroll to a link's target, in a test) waits until those promises have settled, or as long as it chooses; nothing shows differently meanwhile. Before, a processor had no way to know when such a component had drawn. Not breaking: a component that never calls it has drawn when `mount` or `update` returns.
- **Pending packs and data (§4.5, §6.4, §7.4, §8.6, §10.2, §11, §12.3, §13.2).** A host that gets packs or data while a reader views the document may name those it is still getting as pending. A pending import reports nothing, and its names' uses render their fallbacks marked as pending, as a new expanded node, `componentPending` (in the tree schema too), which a renderer shows as loading and which a slot item's `component` marks with `pending: true`. Pending data loads its `fallback` or `null`, without F026. The host, never the processor, decides when a pending source has failed; it is then F026, as before. Before, a pack or data source on its way was F026, as if it couldn't be had. Not breaking: a processor that never fetches while it renders has no pending sources.
- **A failed fetch in lenient mode (§8.6).** A failed fetch without `fallback` is F026 in either mode, with `null` for the data; strict mode fails on it, as on any `F` error. Before, the sentence could be read as `null` with no diagnostic in lenient mode, which §10.1 contradicts. Not breaking.
- **`host` for trusted components too (§7.4, §15).** A processor may give `host` to components of trusted packs as well as permissive ones, the same at both levels, so a component written against it works whichever level its pack is given. Before, `host` was for permissive components alone, though a trusted one reaches more anyway. Not breaking.
- **Slot names with `-` (§5.1, §7.6, §8.1, §10.2).** A slot named with `-`, as the naming convention suggests (`:: #side-panel`), is placed in a `compmd` body with `_` in its path, `{{md.slot.side_panel}}`, as a param is read, and is the camelCase prop or snippet in the React and Svelte bindings (`sidePanel`). Two slots of one component whose names differ only in `-` and `_` are F013, as two params are. Before, such a slot could be declared and filled but never placed. Not breaking: no document could place one.

### 1.0-draft.9, 2026-11-02

- **The colour scheme and a late failure, in the host contract (§7.4, §7.6, §10.2).** The context gains `scheme`, `"light"` or `"dark"`, the scheme the processor shows the component in; when it changes, the processor calls `update` with the same params. It also gains `fail(message)`, for a component that finds after `mount` or `update` returned that it can't draw what it was given: W118 with the message, and the fallback until the next `update`. A throw in `update` is now treated as `fail`, so the component is updated again at the next change; before, a component that threw was never updated again. The React and Svelte bindings pass both in the `compmd` prop. Not breaking: a component that ignores both works as before.
- **Where host metadata's diagnostics are (§2.1).** A diagnostic about a host's metadata, which has no place in the text, is at line 1. Before, the spec didn't say. Not breaking.
- **Library packs (companion, section 5).** A library pack's own libraries are its `peerDependencies`. For a library that can't have two copies, the first pack to ask, in the order the document's imports resolve, decides its version. A library that can't be had (denied, refused, not allowed, no version matching, not a library pack, or in a cycle of libraries) is W121 on the import of the pack that names it, saying why. Before, the companion didn't say which pack decides or what a missing library is. Not breaking.
- **Recursion through code blocks (§7.3, §10.2).** A code block a code renderer renders invokes it, so a `compmd` code renderer whose body leads back to it through such a block is F019, at the block's language, and the block shows its fallback. Before, the spec didn't say whether a rendered block counts as an invocation. Not breaking: such a document never rendered.

### 1.0-draft.8, 2026-11-01

- **Packs on a registry, a companion (§6.4).** New: [*CompMD packs on a registry*](compmd-registry-v1.md), versioned with the spec, for pack authors and for hosts that fetch packs from a registry. It says what a pack on an npm registry must be (the `compmd` field, the keyword `compmd-pack`, built modules as one file, `files`, its size against the host's cap), how a host reads one (policy before any download, the tarball checked against the registry's integrity), who fetches, and what a library pack is: a library packs share through `peerDependencies`, one version per document, with W121 for a second version of one that can't have two copies. §6.4 links to it.
- **A reader's browser may fetch packs, when the host says so (§6.4, §15 *Privacy*).** A processor's configuration may let the reader's browser fetch packs from the registries it names, as a static site with no server needs to; the processor should then tell its readers, since the registry learns the reader's address and the packs' names, never the document. A document can never choose it. Before, packs were always fetched by the processor. Not breaking.
- **Built modules as one file (§6.4).** A built module that imports files of its own can't load where its text is passed, and renders its components' fallbacks with W121; a built module should be one file, with no relative imports.
- **What component code may import (§6.3, §6.4, §7.6, §10.2, §11, §15).** A host-language component's code imports only its binding's runtime, libraries the processor offers, libraries its pack names in `peerDependencies`, and, in a built module, its own files. The runtime is the processor's, one copy for every component, and is never bundled: the spec names it by framework and major version, and the processor says which minor version and modules it has. A built module bundles everything else, and should be one file. Before, the spec said a built module bundles "the libraries it uses" and said nothing about imports inside component code. Not breaking for documents; a built module that bundled its runtime still loads, with a copy of its own.
- **Libraries a processor offers (§6.3, §10.2).** A processor may offer libraries component code imports by their npm name, like ambient packs: not portable, and W113, which now also covers them.
- **Compiling source (§7.6).** JSX and TSX compile with React's automatic runtime, Svelte with Svelte 5's compiler for the client, TypeScript with its types removed; a relative import in source has nothing to resolve against.
- **A pack's `peerDependencies` (§6.4).** A pack names the runtime version and the libraries it needs there; a processor checks them when it resolves the pack, and reports one it doesn't have up front.
- **W121 (§10.2, §11).** New: component code that can't load (an import it may not make, a compile error, a built module that doesn't match its file, or a pack's `peerDependencies` the processor can't meet); its fallback renders. Before, the spec had no diagnostic for these.
- **§15 rule 2.** A strict component's code comes from its pack, its binding's runtime and the libraries the processor provides it, as it always did in practice; the informative note's policy says so too.

### 1.0-draft.7, 2026-10-30

- **Defaults for host-language components (§7.4).** A host-language component's `params` hold the defaults of the declared params its caller doesn't give, as a `compmd` definition's body sees them, and so does the expanded tree. Before, the spec didn't say, and this implementation gave only the params written. Not breaking for documents; a component that supplied its own defaults still works. New case `expand/host-defaults`.
- **Code renderers (§1.1, §2.3, §3, §4.5, §5.1, §6.3, §7, §7.3, §7.7, §10.2, §11, §12.1, §12.3, §17).** A leaf whose signature has `renders: mermaid` (or a list of names of one language) also renders the code blocks of that language, the block's text as its `code` param, which the signature needn't declare: ` ```mermaid ` in a document that imports a `mermaid` code renderer is drawn, and stays a code block in plain renderers and elsewhere. Params go on the info string after the language, read only for rendered blocks; `alt` is the text alternative (W101 without it); two renderers of one language at one level are F023; the `code` param on the info string is F017, and declaring `code` as anything but a required `string` is F009. The expanded tree's `code` node gains `component` and `alt`, in the tree schema too. `component=` defines a component only in a definition language. Not breaking: a code block renders differently only in a document that imports a code renderer. Conformance cases come with the processor's support.
- **Any pack, in the strict sandbox (§6.4, §10.2, §15, §17).** Which packs a document may import is the processor's configuration: by default any pack in the registry, whose code runs in the strict sandbox, one sandbox per document for packs the configuration doesn't list. A processor may allow only listed packs, deny packs as its own policy (not for security, which the sandbox gives), and cap a pack's size; a pack it doesn't allow is F026. Packs are fetched by the processor, never by the reader's browser. Before, §15 said remote component imports needed an allowed origin, as remote data does. Not breaking: documents are unchanged.
- **Built modules (§6.4).** A pack's component file may be a built ES module with its libraries bundled in, which a processor may load by its place in the pack instead of passing its text, from files checked against the pack's integrity.
- **Trust levels (§1.1, §7.4, §15, §17).** A pack's code runs at one of three levels the processor's configuration sets: a strict sandbox (the default, the sandbox as before), a permissive sandbox (the network to the origins listed for its pack, and `host`), or trusted (the host's own code, built with its application, outside a sandbox, which treats params and slots as untrusted input). Before, all component code ran sandboxed, and "packs the host trusts" meant what is now a permissive pack. Not breaking: documents are unchanged.
- **Components the host implements (§6.3, §7.1).** A signature fence alone in an ambient pack declares a component whose code the processor provides, validated against the signature; elsewhere it stays F002. An ambient pack imported by name is always the processor's, never a registry package of that name. New cases `expand/host-signature`, `validate/host-signature-params-F008-F009` and `resolve/ambient-import-by-name`.
- **Unknown type names are F037 (§7.3, §10.2).** A declaration whose type isn't in the grammar, such as `count: numbr`, in a signature, an input or a data `schema`, is F037 at the type name, with the nearest type name. The declaration is kept and takes any value. Before, such a type was accepted silently and checked nothing. Breaking for documents with a misspelt type, which now have an error.
- **Website.** The spec links to the CompMD website, which has the spec as a page and a playground. The spec itself is unchanged.

### 1.0-draft.6, 2026-10-29

- **Links to a passage (§2.3).** A link to a text fragment (`#:~:text=…`) names a passage of the document by its text; a tool that shows the source, such as an editor beside its preview, may select the passage there. No new syntax: they are ordinary links, and the spec says how such tools may read them.

### 1.0-draft.5, 2026-10-27

- **Timestamp and duration getters (§8.2).** The profile's timestamp and duration operations include CEL's getters, `getFullYear` to `getMilliseconds`, so a document can show the time of day. A timestamp's getters take a time zone and, unlike CEL's, use `md.tz` without one. Before, the getters weren't named, and a processor could leave them out.
- **Numbers as text (§8.1, §8.2).** Interpolation and `string()` write a number as JavaScript's `String(n)` does: plain from 10⁻⁶ up to 10²¹, with an exponent outside (`1e+21`, `1.5e-7`), and `NaN`, `Infinity` and `-Infinity`. Before, the form of very large and very small numbers wasn't said.
- **Number map keys match by value (§8.2).** As in CEL, `{1: "a"}[1u]` and `{1: "a"}[1.0]` are `"a"`, so `md.groupBy` on a field of whole numbers from data gives `int` keys.
- **Inline math follows Pandoc's rule in full (§2.3).** Outside a `{…}` group, a `$` with white space on its left ends the attempt, and the opening `$` is text, as in Pandoc. Before, a later valid closer could reach back past it, so `It costs $5 and $6. Math $x^2$` made `5 and $6. Math $x^2` math; now only `$x^2$` is. Breaking for documents that relied on the old reading. New case `base-syntax/math-dollar-after-space`, checked against Pandoc 3.12.1.
- **Code spans in fallbacks (§3.1, §3.2 rule 9).** A code span binds tighter than a fallback's brackets, as in CommonMark's link text: `:a[b `c]` d]` has the fallback ``b `c]` d``, as plain renderers show it. Before, the `]` inside the code span ended the fallback. Breaking for such fallbacks. New case `inline/fallback-code-span`.
- **Terms (§1.1).** A glossary of the spec's terms, each with its section. "Container" means only a `:::` component; the box a block's breakpoints follow is its *nearest box*.
- **Breakpoints follow the nearest box (§9.3).** A block's params follow the width of its nearest box, the term §9.2 uses for positions, rather than its parent's: list items, quotes and alerts don't count, so a component in a list item inside a box follows the box. A new informative §9.5 shows which box breakpoints follow in each case. Only the wording changes, since list items and quotes were never boxes.
- **W114 wherever a box's width comes from its content (§9.3, §10.2).** A box whose blocks use breakpoints shrinks to nothing wherever its width would come from its content. W114 was only for a box in a `row`; it now also covers a box in a `stack` that isn't stretched across it, a box in a `grid` with `justify-self`, and a positioned box without both inline insets. A document may now have W114 where it had none. New cases: `expand/column-child-width-W114`, `expand/grid-child-width-W114`, `expand/positioned-width-W114`, and `expand/block-child-width` with none.
- **Slot items and their width (§7.4).** A host-language component that lays its items out by their content gives an item a width when the block in it uses breakpoints.

### 1.0-draft.4, 2026-10-24

- **The reference rendering (§13.1).** The informative HTML and CSS rendering of the built-ins is `@compmd/render`'s, in [`render/`](../npm-packages/render/README.md#the-reference-rendering-of-the-built-ins). The spec itself is unchanged.
- **Breakpoints follow the parent's width (§9.3, §10.2; W114).** Every param of a block, its layout among them, follows its parent's width; before, a block's own layout followed its own width, which CSS can't express (an element's styles follow an ancestor's width, not its own). The two differ only for a block much narrower than its parent: `::: grid {width=40% md:grid-template-columns="1fr 1fr"}` on a wide page now has two columns. W114 is for a block in a `row` whose *children* use breakpoints, as §9.3 said; a block whose own layout uses breakpoints no longer gets it. Case `expand/row-child-width-W114` is updated.
- **Origins (§12.3, §13.1, §13.2, §17).** A new optional feature, `origins`: every expanded node has `origin`, the range of the processed document that made it, with its `occurrence` among the nodes before it with the same range. A node from a definition's body takes its invocation's origin, so an editor can keep what it rendered for a node through an edit. Keys for matching nodes across edits are the editor's, not the format's. The tree schema has `origin`, and a new case is `expand/origins`.
- **Record keys, an open issue (§17).** `each` iterations and template slot instances are told apart by index, not by record, so state shown for one record moves to another when records are added in front. A record key is to be decided.
- **Author.** The spec names its author.
